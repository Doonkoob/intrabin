# Intrabin v0.2.0

## Monitoring by node
- Recent checks identify the monitoring node, with a node filter for inspecting one worker's responses and errors.
- Monitor details include a separate latency line for each node, a shared scale, per-point details and a clickable legend. Failed or missing buckets break the line.
- Long-range charts use replicated hourly node aggregates so they survive raw-result retention and leader failover.

## Cluster updates
- Confirming an update on the leader records a durable Raft plan before restarting it. Once it returns, the remaining members update one at a time, non-voters first.
- The current leader resumes the plan after elections. A node's target version is pinned to the confirmed release, even if a newer release appears during the rollout.
- Settings shows each node's progress and failures. A failed rollout stops; an administrator can retry the remaining nodes after fixing the cause.
- Peer update commands require cluster mTLS, current leadership, an open quorum gate and a matching replicated plan. Every node verifies the release with GitHub and uses its own host agent for backup and installation.

## Resource use and update progress
- Installations and updates build or pull each enabled service image separately, then start containers sequentially. Startup cannot trigger an implicit image build or download.
- The update dialog and Settings show completed deployment milestones, the current service and progress through backup, image preparation, restart and health verification. Cluster progress includes the active node's deployment progress.
- Build failures stop before the next service, retain the failed stage's progress and never report completion. Completion is reported only after all containers are started and the new version passes the host health check.

## Versions and release notes
- Settings lists recent stable releases and their changes.
- Releases use vMAJOR.MINOR.PATCH tags. The tag, VERSION file, image labels and published release notes must agree.
- Docker builds avoid the extra Dockerfile frontend pull and the gcr.io runtime dependency.

## First upgrade from older versions
Versions before v0.2.0 do not understand cluster update commands. Upgrade each existing node to v0.2.0 once (from its own Update button, or `sudo intrabin update --to v0.2.0`). Re-run the installer if its host update agent is missing. Subsequent updates started on the leader automatically update the remaining members. Each node needs outbound GitHub/registry access and a working host agent.

The first leader restart can cause a brief election; a one- or two-voter cluster temporarily loses management availability while a voter restarts. Rollouts pause while quorum or member reachability is missing. Database backups are retained; an application-startup failure is reported for manual recovery rather than automatically restoring cluster data.
